# Decisions Log

Dated, one-line-rationale entries for every non-obvious design decision made during this project (rule interpretations, reward values, discretization schemes, hyperparameter choices, etc.). This is primary source material for the dissertation's methodology chapter — append as decisions are made, not retroactively.

Format: `YYYY-MM-DD — decision — rationale`

## Step 2 — Rules Specification

- 2026-08-11 — Blockades (2+ own tokens on one main-track square) fully block opponent landing and passage, and cannot be captured — chosen as the classic/most common Ludo convention; keeps blockades a meaningful defensive mechanic rather than a cosmetic one.
- 2026-08-11 — Exact-count-to-home required: a token with no exact roll to land precisely on relative_position 57 has no legal move that turn (other tokens may still move) — standard rule, preserves late-game tension rather than letting tokens "cap out" at home.
- 2026-08-11 — Three consecutive sixes forfeits the *entire* turn, including moves already made from the first two sixes, not just the third roll — chosen over the "only discard the third roll" alternative as the more well-known "three sixes = bust" house rule; has a real engine implication (turn must be buffered before commit, see rules_spec.md §9) that was flagged back for review.
- 2026-08-11 — A roll of 6 always grants a bonus roll, even if it resulted in no usable move (e.g. Base already has a token, or the only eligible token is blocked) — bonus-roll eligibility is tied to the die value itself, not to whether the roll was usable, matching standard implementations.
- 2026-08-11 — Board geometry fixed: 52-square shared main track, entry squares spaced 13 apart (global 0/13/26/39), 8 safe squares (4 entry + 4 star squares at +8 from each entry), 57-square total path per token (51 main-track + 6 home-column) — standard classic-Ludo numeric layout; this is the fixed contract Step 3's coordinate transforms implement against.
- 2026-08-11 — No stacking allowed in the home column: a token cannot land on a home-column square already occupied by another of the player's own tokens — blockades are a main-track-only mechanic, home column is a single-file private corridor.
- 2026-08-11 — Bonus rolls are also granted for capturing an opponent token and for a token reaching Home, not only for rolling a 6 (at most one bonus roll per die roll even if multiple conditions are met) — matches the standard three-trigger convention used in most digital Ludo implementations, chosen for a richer/more standard bonus-roll dynamic than a 6-only rule.
- 2026-08-11 — Three-sixes bust will be implemented via buffer-before-commit (simulate the full six-streak before mutating board state) rather than snapshot-and-rollback — avoids needing to un-resolve captures/other state changes if the third six busts the turn.
- 2026-08-11 — Episode/game ends immediately when any one player finishes all 4 tokens (first-to-finish, single winner) — no continued play to rank 2nd-4th place. Chosen over the full-ranking variant for a cleaner binary win/loss terminal signal and lower engine complexity, appropriate for the single-agent-vs-fixed-opponents RL framing.

## Step 3 — Board & State Representation

- 2026-08-11 — Token position stored as a single `relative_position` integer per token (-1 = Base, 0-56 = on track, 57 = Home) rather than a separate state enum plus position field — the rules_spec.md numbering already makes state unambiguous from the value alone, so a second field would be redundant.
- 2026-08-11 — Observation encoding is egocentric by construction: `encode_observation` always places the acting player's 4 tokens first, then the other three seats in turn order starting from the acting player's next opponent, rather than a fixed absolute-player-index layout. Reason: a single DQN trained this way only has to learn one seat's worth of strategy and can act correctly regardless of which of the 4 absolute seats it's controlling in a given episode — avoids needing 4x the training data to cover each starting position separately. Verified by test (`test_egocentric_reordering_moves_acting_players_tokens_to_first_block`) that the same absolute board state produces a reordered observation when queried from a different acting player.
- 2026-08-11 — Per-token feature vector fixed at 4 values (`normalized_position`, `is_base`, `is_home`, `is_safe`), giving a 64-dim flat observation (4 seats x 4 tokens x 4 features) — chosen as a minimal but complete summary of what the rules engine needs to expose per token; Step 8 may extend this if the network needs more signal, but this is the tested baseline contract.

## Step 4 — Core Rules Engine

- 2026-08-14 — Reward values fixed as placeholders in `env/rewards.py`: exit_base +0.2, safe_square_entry +0.2, capture_opponent +1.0, reach_home +1.0, win +2.0, got_captured -1.0, loss -2.0, truncated -0.5 — ordered by real game importance (small positional progress < single-token events < whole-game outcome). Explicitly flagged as tunable, subject to the planned reward-shaping ablation in Step 11.
- 2026-08-14 — Added `got_captured`, `win`, and `loss` as reward categories beyond the 5 named in the build plan's Step 4.5 (capture, exit-base, enter-home, safe-zone entry, truncation) — a working reward signal needs to penalize being captured and score the terminal win/loss outcome; these were an omission from the plan's illustrative list, not a deliberate scope decision to exclude them.
- 2026-08-14 — `env/turns.py::play_turn` resolves a full player turn (including bonus rolls and the three-sixes bust) via a synchronous `choose_action_fn` callback. This is reused as-is for scripted/fixed opponents in Step 5's turn-cycling loop, but the learning agent's own turn will be decomposed roll-by-roll in Step 5 instead, since each of its decisions must cross a real `gym.Env.step()` boundary and can't be answered synchronously via callback.

## Step 5 — Gymnasium Wrapper + Validation

- 2026-08-14 — `LudoEnv`'s internal turn-cycling loop (`_run_until_agent_turn_or_done`) is implemented as a single flat `while` loop rather than the recursive design first drafted — a recursive version re-entered itself once per auto-skipped turn, so a fully stalled game (nobody able to move for `max_turns` turns, e.g. `test_repeated_no_legal_move_turns_do_not_stall_and_truncate_cleanly`) would recurse roughly `max_turns` deep and risk hitting Python's recursion limit at the default `max_turns=1000`. The iterative version has no such ceiling.
- 2026-08-14 — Opponent turns are fast-forwarded synchronously via `GameState.step_turn` (reusing Step 4's `play_turn` unchanged); the agent's own turn is decomposed roll-by-roll inside the same loop, pausing whenever a real decision is needed. Confirms the split anticipated in the Step 4 entry above.
- 2026-08-14 — Reward attribution for opponent captures (5.2) is implemented via a `_pending_captured_penalty` accumulator: captures against the agent detected during fast-forwarded opponent turns are added to this accumulator, which is only read (and reset) at the start of the agent's *next* `step()` call — naturally keeping the captured penalty out of the `step()` call during which it occurred, without needing special-case logic.
- 2026-08-14 — No baseline agents exist yet (Step 7), so `LudoEnv` defaults to a uniformly-random opponent policy when none is supplied, using the env's own seeded rng. `opponent_policy` is a constructor parameter so Step 7's baseline agents can be swapped in later without changing `LudoEnv` itself.
- 2026-08-15 — Bug found and fixed during a Steps 1-5 audit: if an opponent captured the agent's token during a fast-forward that then ended the episode (opponent win or truncation) before the agent's next `step()` call, `_pending_captured_penalty` was queued but never paid out, since it was only ever read at the top of the *next* `step()` call — which never came. Fixed by paying out any leftover pending penalty immediately whenever `step()` detects the episode just ended. Regression test: `test_captured_penalty_is_paid_immediately_if_episode_ends_before_next_step`.

## Step 6 — Decide Agent Scope

- 2026-08-15 — Final agent list confirmed as Random, Heuristic, Tabular Q-learning, DQN, and Double DQN (`docs/agents_spec.md`) — the minimum set needed for the dissertation's central comparison (naive baselines vs classical non-deep RL vs deep RL and its overestimation-bias variant), with each entry either a required baseline or a near-free extension.
- 2026-08-15 — SARSA and Monte Carlo Tree Search were both considered (raised from the literature review) and explicitly deferred rather than dropped. SARSA is cheap once Tabular Q-learning's discretization scheme exists, but isn't needed for the core contribution. MCTS's build cost is comparable to DQN itself (tree search with dice chance-nodes) and it costs real compute per decision at evaluation time, which could slow the Step 11 tournament — worth revisiting as a stretch goal only after the core five are trained and evaluated, so it can't put the core result at risk.

## Step 7 — Baseline Agents

- 2026-08-15 — Heuristic agent priority (capture > exit base > enter home > form/join blockade > advance) is computed by read-only board inspection per candidate token (no cloning/simulating the move), since every category is derivable from the current board plus arithmetic (destination = position + roll) without needing to actually apply the move first. Ties within a category are broken by preferring the most-advanced token, matching the "advance the most-advanced token generically" framing already in `docs/agents_spec.md`.
- 2026-08-15 — Tabular Q-learning's state discretization (`agents/tabular_q_agent.py::discretize_state`) reduces each of the acting player's own 4 tokens to one of 12 values: a 6-way progress zone (Base / early / mid / late main-track / home column / Home) combined with a 1-bit "threatened" flag (an opponent token sits within 6 squares behind on an unsafe square, so could capture next roll). Full state space is at most 12^4 ≈ 20,736 entries — small enough to train quickly, but built around the two factors (progress, capture risk) that most plausibly matter for skillful Ludo play, rather than an arbitrarily coarse bucketing chosen just to shrink the table. Deliberately simplified: the threat check doesn't account for path-blocking (an opponent "within 6" who is actually blocked by an intervening blockade is still flagged as threatening) — a documented approximation, not an oversight. The scheme is also seat-agnostic like the DQN's egocentric encoding: only the acting player's own zones/threat flags are encoded, never an opponent's absolute seat, so the same table is reusable regardless of which seat the agent occupies.
- 2026-08-15 — `TabularQAgent.update()` masks the next-state max over `next_legal_tokens` only, mirroring the masked-Bellman-target discipline already flagged as critical for DQN in Step 8.5 — implemented correctly from the start rather than retrofitted later.
- 2026-08-15 — The 7.4 regression test (`tests/test_baseline_hierarchy.py`) initially used `max_turns=200` (matching Step 5's smoke test) and produced a heuristic win rate of ~1%, not because the Heuristic agent is weak but because at that cap, 49/50 sampled games never finished at all (truncated with nobody home) — 200 turns is far too short for 4 tokens x 57 squares of movement, especially with random opponents resetting each other's progress via captures. Raised to `max_turns=1000` (matching `GameState`'s own default), which brings games to ~100% natural completion. Worth carrying into Step 10's training-episode-length planning: real games need on the order of hundreds of turns, not tens.

## Step 8 — DQN Architecture

- 2026-08-15 — `QNetwork` (`agents/dqn_network.py`) is 3 linear layers with ReLU after the first two only — no activation on the output layer, since Q-values are unbounded real numbers, not something that should be squashed. `hidden_size` defaults to 128, the only architectural knob exposed; kept small deliberately given the 64-dim input and CPU-only training.
- 2026-08-15 — Masked action selection (8.4) and the masked Bellman target (8.5/8.7) both mask by setting illegal entries to `-inf` before taking a max/argmax, rather than filtering the tensor down to legal entries only — keeps every op fully vectorized across a batch (no per-row Python loops), and `-inf` guarantees a legal action always wins the comparison regardless of the actual Q-value magnitudes.
- 2026-08-15 — Added an explicit guard in `compute_targets` for a next state with zero legal actions (`no_legal_next_action`), treating it as zero future value instead of leaving `-inf` to propagate into the target (which would corrupt the loss into NaN). Per the env's own design this should never actually occur in real transitions — `LudoEnv` never hands the agent a state with a fully-masked action vector — but it's cheap defensive coding in the same spirit as the `max_bonus_rolls` circuit breaker in `env/turns.py`, and it's unit-tested directly (`test_target_with_no_legal_next_action_is_treated_as_zero_future_value`) rather than left as untested dead code.
- 2026-08-15 — Double DQN (8.7) is implemented as a `double_dqn: bool` flag on the same `DQNAgent`/`compute_targets`, not a separate class — the two differ only in which network's argmax picks the next action, so duplicating the surrounding masking/batching code for a second class would just be copy-paste risk with no benefit. Verified to actually diverge from plain DQN using a hand-constructed transition where the online and target networks are forced (via zeroed hidden-layer weights and a fixed output bias) to output known, deliberately conflicting Q-vectors — `test_double_dqn_target_diverges_from_plain_dqn_target` — rather than trusting the two formulas differ just by inspection.
- 2026-08-15 — 8.6's "verify numerically on a tiny toy MDP" is a fully synthetic 2-action, single-state, immediately-terminal MDP with a known ground truth (action 0 always worth +1.0, action 1 always worth -1.0, `gamma=0`) — deliberately not the real Ludo engine at any scale. This is a different, smaller check than Step 9's later "toy environment" (a simplified but real Ludo env); 8.6 only needs to prove the loss function and optimizer actually drive Q-values toward correct values, with no game logic involved at all.

## Step 9 — Toy Environment Validation

- 2026-08-15 — `ToyLudoEnv` (`env/toy_env.py`) reuses the real `board.py`/`legal_moves.py`/`moves.py`/`rewards.py`/`turns.py` machinery directly (not a reimplementation), stripping out only the multi-agent turn-cycling and dice randomness — since it's specifically the DQN's integration with the *real* masking/reward code that Step 9 needs to validate, not a second, separate toy rules engine that could itself hide bugs.
- 2026-08-15 — "Fixed/no-dice" (9.1) is implemented as a short deterministic repeating roll sequence `(6, 3, 5, 2, 6, 4, 1, 6, 3, 5)`, not a single constant roll — a constant non-6 roll would permanently lock any Base token out forever (never exercising base-exit masking), while a constant roll of 6 would make masking trivially rare (nearly everything stays legal). The varied fixed sequence produces genuine, reproducible masking pressure (base-exit sometimes possible, overshoot near Home sometimes blocked) without any real randomness.
- 2026-08-15 — The starting layout (`_default_start_positions`) deliberately spans Base, mid-track, near-Home, and already-Home (one token per zone) specifically so the action mask is never trivially all-legal at any point in the episode — directly targeting the masking-discipline risk 9.1 calls out as the highest-risk DQN-specific bug class.
- 2026-08-15 — Deliberately dropped from the toy env: bonus rolls and the three-sixes bust. Both are turn-*structure* realism already thoroughly tested in Steps 4-5; re-implementing them here would only add surface area that could itself be buggy, muddying whether a toy-env failure means "the DQN is broken" or "the toy env's own turn logic is broken." Every scripted roll is a single independent decision, full stop.
- 2026-08-15 — `training/toy_trainer.py` is intentionally minimal (no checkpointing, no logging beyond an in-memory loss list, no seed sweeps) — Step 10 will need a substantially more complete training loop for the real stochastic 4-player environment, but building that now would be scope creep for what's meant to be the cheapest possible bug-catching checkpoint.
- 2026-08-15 — Hyperparameters for the 9.2/9.3 convergence check (`tests/test_toy_dqn_convergence.py`) were chosen empirically, not guessed: tried 100/150/300 training episodes directly and measured actual loss trend and greedy-policy win rate before picking numbers. 150 episodes (~13-16s) reliably drops average loss by roughly 10x and yields a 100% greedy win rate over 30 evaluation episodes in testing, well clear of the regression thresholds committed in the test (loss must at least halve; win rate must clear 90%).
- 2026-08-15 — Extended the same toy convergence check to Double DQN (`test_double_dqn_loss_decreases_and_agent_reliably_reaches_home`), not required by the plan's Step 9 wording (which only names "DQN") but essentially free given the two only differ by the `double_dqn` constructor flag. Same result as plain DQN with identical hyperparameters: loss drops ~11.6x (0.1201 to 0.0103), 150/150 training wins, 100% greedy win rate over 30 evaluation episodes.
- 2026-08-15 — A calibration run (throwaway script, not committed) measured real per-episode cost on the full `LudoEnv`: ~46.5ms/episode gameplay-only, ~277.5ms/episode with DQN training active (dominated by ~3ms/update training overhead, not simulation). Used to reason about Step 10's total time budget before writing any of its code; genuinely unknown variable remains how many episodes DQN needs to actually converge on the real stochastic game, which calibration can't answer — only real training can.

## Step 10 — Full Training

- 2026-08-15 — `TrainingConfig` (`training/config.py`) is a plain dataclass serialized to JSON, not YAML — avoids adding a new dependency (PyYAML) for something the stdlib `json` module already handles fully. `save_config` also automatically snapshots the current `REWARD_CONFIG` dict and the git commit hash into the saved file, satisfying 10.3's "hyperparameters, reward dict, seed" requirement as a traceability record. This is a snapshot, not an override mechanism — `TrainingConfig` has no field that actually changes reward computation yet; building that injection machinery is deliberately deferred to Step 11.4, when the reward-shaping ablation actually needs it, rather than built speculatively now.
- 2026-08-15 — Training is split into two trainer classes, `DQNTrainer` and `TabularQTrainer` (`training/dqn_trainer.py`, `training/tabular_q_trainer.py`), rather than one generic trainer — the two learning agents fundamentally differ in mechanics (DQN needs the 64-dim `encode_observation` vector plus batched replay; Tabular Q needs the discretized board state plus a single online `update()` per move, no buffer at all). Unified only where it's genuinely shared: both expose `run_episode()` returning the same `EpisodeStats`, and `select_greedy_action()` for evaluation — letting `training/evaluate.py` and the checkpoint-selection logic in `run_training.py` work identically regardless of which agent is being trained.
- 2026-08-15 — Epsilon decay (`training/schedules.py::linear_epsilon`) is owned entirely by the training loop, not the agent classes — `DQNAgent`/`TabularQAgent`'s `epsilon` was already a plain mutable attribute by design (Steps 7-8), so the loop just sets `agent.epsilon` before each episode. Avoids touching or re-testing already-reviewed agent code for a concern (a schedule over episodes) that belongs to the training loop, not the agent's own decision logic.
- 2026-08-15 — Checkpoints (`training/checkpoint.py`) use different formats per agent type — `torch.save` (`.pt`) for DQN/Double DQN's network weights, `pickle` (`.pkl`) for Tabular Q's Q-table — since a Q-table (a dict keyed by tuples) isn't tensor data and pickle is the simplest correct serialization for it via the stdlib, with no new dependency. Every checkpoint embeds `episode`, `config`, `git_commit`, and `eval_win_rate` per 10.6's explicit requirement. `run_training` saves both a periodic checkpoint (`episode_N.*`) and a separately-tracked `best.*` (by evaluation win rate, not periodic recency), since DQN training curves aren't monotonic and the periodically-scheduled checkpoint isn't guaranteed to be the best one seen.
- 2026-08-15 — `training/sweep.py::generate_sweep_configs` only *generates* the 12-config grid (2 learning rates x 2 target-sync frequencies x 3 epsilon-decay schedules — the 3 hyperparameters named in 10.4) — it deliberately does not run any of them. Per explicit user instruction, Step 10's code was built without executing any real training; how many of the generated configs actually get trained, and for how many episodes, is the user's call once they've reviewed the code, informed by the calibration numbers above.
- 2026-08-15 — Every Step 10 test uses deliberately tiny episode counts (2-5) purely to prove the pipeline is wired correctly (config save/load, CSV rows written, checkpoints produced with correct metadata, the Q-table/replay buffer actually populate) — these are explicitly not claims about training quality, the same distinction already established for Step 9's toy checkpoint vs. real training.
- 2026-08-15 — Added `runs/` to `.gitignore` proactively, before any real training output exists — checkpoints and per-run logs are large, regenerable artifacts, not source code, and shouldn't end up tracked once real runs start producing them.
- 2026-08-15 — Bug found and fixed via the user's own first manual test run (200 episodes): `EpisodeStats.won` and `evaluate()`'s win counting were both computed as `won=terminated`, but `terminated` is true whenever the *game* ends in a win by anyone, including an opponent beating the agent — every one of the 200 test episodes was logged as `won=1`, even in the first episode at ~99.9% random exploration, which made the bug obvious rather than silent. Fixed by extracting one shared helper, `training/episode_stats.py::agent_won(terminated, info, agent_player_id)`, checking `info["winner"] == agent_player_id` specifically, and using it in all three places that had independently duplicated the same wrong check (`DQNTrainer.run_episode`, `TabularQTrainer.run_episode`, `evaluate()`). Re-running the same 200-episode test after the fix gives a plausible 6/200 (3%) win rate. This also means `evaluate()`'s win rate — used to pick each run's "best" checkpoint — was previously nonfunctional as a selection signal; any checkpoints saved before this fix should not be trusted and should be regenerated.
- 2026-08-16 — User ran a 5,000-episode manual sanity check (single DQN config, Heuristic opponent) before committing to the full scope. Result: win rate rose from 2.8% (first 500 episodes) to 6.2% (last 500), average reward rose from -0.774 to -0.246, and loss dropped through roughly episode 3,000 then plateaued around 0.23-0.24 rather than continuing to fall. Judged a genuine pass — real, if modest, learning signal, nothing diverging — with the loss plateau flagged as something to watch in the full run, not a blocker (loss reflects fit to the network's own shifting targets, not policy quality directly, and reward/win-rate kept improving even while loss was flat).
- 2026-08-16 — `run_training()` now returns the run's best evaluation win rate (previously returned `None`) — a minimal, backward-compatible signature change needed so an orchestrator can compare sweep configs against each other without re-opening each one's saved checkpoint just to read one number back out.
- 2026-08-16 — Built `training/run_full_training.py` to orchestrate the full Step 10 scope (12 sweep configs + 5 seeds each for DQN/Double DQN/Tabular-Q = 27 runs) behind one command. The hyperparameter sweep (10.4) is run for plain DQN only, not separately for Double DQN — the winning config's hyperparameters are reused for Double DQN's final runs too, since the two share the exact same hyperparameter surface (learning rate, target-sync frequency, epsilon decay) and differ only in the target computation itself (already covered by Step 8's Double DQN unit tests), so a second 12-config sweep would double sweep cost for a near-identical answer. Tabular Q isn't part of the sweep at all — 10.4 explicitly names hyperparameters specific to DQN (e.g. target-sync frequency doesn't apply to a tabular method), so it just runs its final multi-seed phase with its own existing defaults.
- 2026-08-16 — While testing the orchestrator end-to-end (tiny 2-episode runs), a tiny smoke test took 196s instead of the expected few seconds — traced to `eval_episodes` defaulting to 50 and never being threaded through the orchestrator, so every one of the 15 tiny training runs still ran a full 50-episode evaluation. Fixed by exposing `eval_episodes` as a parameter on `run_full_training` (and its CLI), rather than leaving it hardcoded to the `TrainingConfig` default — dropped the same test back to ~33s once the test passed a small value explicitly. Not a correctness bug, but worth fixing since an unexposed hardcoded value would have made tuning evaluation cost for a real run impossible without editing the orchestrator's source.
- 2026-08-17 — Full training scope (12-config sweep + 5 seeds x {DQN, Double DQN, Tabular Q} = 27 runs, 10,000 episodes each final run, `runs/full/`) completed end to end via `training/run_full_training.py`, user-run in the background over roughly 24 hours real-world (throughput held steady around 395-420ms/episode against the Heuristic opponent throughout, no crashes or divergence). Winning swept hyperparameters: learning_rate=0.0005, target_sync_every_steps=1000, epsilon_decay_episodes=6000 (14% eval win rate in the sweep, best of 12). Final 5-seed evaluation win rates (50 greedy episodes per seed, one agent seat vs. 3 Heuristic opponents): DQN 6/8/6/8/12% (mean 8.0%), Double DQN 4/4/10/12/6% (mean 7.2%), Tabular Q 10/8/4/4/8% (mean 6.8%).
- 2026-08-17 — Measured a Random-agent baseline under identical conditions (one seat, 3 Heuristic opponents, `max_turns=1000`) to give the final win rates something real to compare against, since a flat 25% "no-skill" baseline doesn't apply here (opponents are Heuristic, not Random). Result: 4.0% win rate over 500 greedy episodes (20/500). Two-proportion z-test against each agent's pooled 250-episode eval sample: DQN's 8.0% is significantly above random (z≈2.30, p≈0.02); Double DQN's 7.2% is borderline (z≈1.88, p≈0.06); Tabular Q's 6.8% does not clear conventional significance (z≈1.67, p≈0.10). Interpretation: all three learned agents show a real, directionally consistent improvement over random play (roughly 1.7-2x), so Step 10's "genuine learning happened" bar is met, but none come close to matching the Heuristic opponents' own performance (estimated at the time as "~30%+ per seat"; **corrected 2026-09-22 to ~22-25%** — see the Step 11 code-review entry, which measured it directly rather than estimating), and the three learning methods are statistically much closer to each other than any of them is to random. This is treated as Step 10's checkpoint being met (stable win rate across seeds, and above baseline), not as a failure — the small, undifferentiated gap between DQN/Double DQN/Tabular Q is itself flagged as a limitation/discussion point (see below) rather than assumed to be a bug, since all three trainers independently show the same ceiling.
- 2026-08-17 — Candidate explanations logged for why DQN did not clearly outperform Tabular Q despite the added function-approximation machinery, for the dissertation's limitations/discussion section: (1) the hyperparameter sweep (10.4) was deliberately scoped to 3 DQN-specific hyperparameters over 12 configs for hardware/time reasons — a DQN this lightly tuned may simply not be operating near its ceiling, while Tabular Q used its untuned defaults throughout, so the comparison may currently be "lightly-tuned DQN vs. untuned Tabular Q" rather than each method's best case; (2) 10,000 episodes trains a Tabular Q table (a bounded discretized state space) to convergence far faster than it fully trains a 64-dim neural network's generalization behavior, so the episode budget may favor the tabular method's simplicity rather than being neutral between them; (3) the 64-dim `encode_observation` feature set (Step 3) was designed as "a minimal but complete summary," not iterated on for RL-signal richness — DQN's main theoretical advantage over a hand-discretized table is exploiting generalizable structure in a richer feature space, so a thin observation may be capping exactly the capability DQN is supposed to add; (4) the reward shaping (`env/rewards.py`) is still the original Step 4 placeholder values, never tuned or ablated (that ablation is planned for Step 11.4) — sparse/uninformative shaping caps what any of the three methods can learn regardless of representational power, and would tend to compress the gap between them.

## Step 11 — Evaluation (code only; user will run manually, per explicit instruction)

- 2026-08-17 — Reward injection built for real (11.4): every function in `env/rewards.py` now takes an optional `config` override (defaulting to the module-level `REWARD_CONFIG`), `LudoEnv` accepts a `reward_config` constructor arg and threads it through every reward call site, and `TrainingConfig` gained a `reward_mode: "dense" | "sparse"` field that `run_training.py::build_reward_config` resolves. `env/rewards.py::SPARSE_REWARD_CONFIG` zeroes every shaping term but keeps `win`/`loss` at the same magnitude as the dense config, so the ablation isolates shaping's effect rather than conflating it with a change in terminal reward scale. This is exactly the injection machinery Step 10's config.py entry (2026-08-15) deliberately deferred until it was actually needed.
- 2026-08-17 — `LudoEnv`'s `info` dict gained two new keys, `episode_captures_made` and `episode_times_captured` (running per-episode counts, reset each `reset()`) — needed for 11.3's capture-to-death ratio metric, which nothing in the existing API contract exposed. Purely additive to `docs/env_api.md`'s contract, no existing key changed meaning.
- 2026-08-17 — `training/statistics.py` implements the Wilson confidence interval, a two-proportion z-test, and mean/std-across-seeds from closed-form formulas (`math.erf` for the normal CDF) rather than adding scipy as a dependency, since `requirements.txt` deliberately doesn't include it and these three formulas are standard/well-defined enough not to need a library.
- 2026-08-17 — `training/tournament.py` evaluates every agent type (trained checkpoints and the Random/Heuristic baselines) through one shared `GreedyPolicy` interface — trained agents' `select_action`/`__call__` are wrapped directly, and `wrap_choose_action_fn` adapts the existing `ChooseActionFn` baseline signature to match — so the same `run_tournament` code path produces directly comparable results regardless of what's being evaluated, rather than duplicating the rollout loop per agent type the way the pre-Step-11 code duplicated `won` logic three times (see the 2026-08-15 bug entry above).
- 2026-08-17 — The reward-shaping ablation (11.4, `run_full_evaluation.py::run_reward_ablation_training`) is scoped to DQN only, not all three agent types — same hardware/time-budget reasoning already used to scope Step 10's hyperparameter sweep to DQN-only. It reuses the sweep's winning hyperparameters (read from `runs/full/summary.json`) rather than re-sweeping for the sparse variant.
- 2026-08-17 — `run_full_evaluation.py` also evaluates a Heuristic agent through the exact same one-seat-vs-3-Heuristic-opponents tournament setup (`heuristic_mirror`), alongside the Random baseline — added after the baseline discussion made clear that a flat 25% "no-skill" reference doesn't mean anything here (opponents aren't random), so a properly-matched competitor's own score in the identical setup is needed as an interpretive anchor for what "good" looks like in this 4-player mix.
- 2026-08-17 — **Real bug found and fixed while building Step 11's tests, not by code review**: `LudoEnv.reset()` can return an already-truncated episode with no pending decision, if the agent's tokens never roll a 6 for long enough that `max_turns` is reached during `reset()`'s own fast-forward, before the agent's first real decision. Gymnasium's `reset()` never reports `terminated`/`truncated` (only `step()` does), so nothing in the public API let a caller detect this — `evaluate()`, both trainers' `run_episode()`, and the new `training/tournament.py` all hardcoded `terminated = truncated = False` right after `reset()`, so the very next `step()` call raised `RuntimeError: step() called with no pending decision`. Reproduced via `tests/test_run_full_evaluation.py`'s tiny-`max_turns` fake-checkpoint fixture (a ~1% per-episode event at `max_turns=100`, given ~25 agent attempts at `(5/6)^25`). First fix attempt (retrying `reset()` with a fresh `GameState` until a decision was pending) was wrong and caused a genuine infinite loop against `tests/test_ludo_env.py`'s existing deliberately-never-rolls-six scripted RNG (used to test clean truncation) — caught because it hung the test suite for real, killed and diagnosed rather than assumed fixed. Corrected fix: `reset()` is left as-is (already-truncated-with-no-decision is valid, expected behavior, matching the existing truncation test's intent), and each of the four call sites now reads `env.game.terminated`/`env.game.truncated` right after `reset()` instead of assuming `False` — this correctly treats the rare case as a valid zero-length episode/loss, with no retry and no risk of looping. `docs/env_api.md` documents this as the caller contract. At the real training/tournament `max_turns=1000` used throughout Step 10, the probability is `(5/6)^250 ≈ 1e-20` — effectively never, so this did not affect the already-completed Step 10 results, but it's a real landmine at the smaller `max_turns` a fast Step 11 tournament might use. Regression tests: `tests/test_ludo_env.py::test_reset_can_leave_an_already_truncated_game_with_no_pending_decision`, `tests/test_evaluate.py::test_evaluate_handles_an_already_truncated_episode_without_crashing`, `tests/test_dqn_trainer.py::test_run_episode_handles_an_already_truncated_episode_without_crashing`, `tests/test_tabular_q_trainer.py::test_run_episode_handles_an_already_truncated_episode_without_crashing`.

## Step 11.5 — Full code review (2026-09-22)

- 2026-09-22 — **Dice stream was never seeded; no training run was reproducible.** `run_training` built `LudoEnv(...)` with no `rng=`, so `reset()` fell back to `self.np_random`, and `super().reset(seed=None)` never seeds it — Gymnasium drew from OS entropy. Verified by rolling two fresh envs and getting different sequences. `config.seed` therefore only ever controlled weight init, exploration and replay sampling, while the dice — by far the largest variance source in Ludo — were uncontrolled, which quietly undercut the config/git-hash traceability record. Fixed with `run_training.build_env(config, dice_seed)`, plus `TRAINING_DICE_SEED_OFFSET`/`EVAL_DICE_SEED_OFFSET` so training, evaluation and Step 11's tournaments stay on distinct but reproducible streams. Step 10's completed runs are *not* retroactively reproducible; this is noted as a limitation of those results rather than fixed in them.
- 2026-09-22 — **Three-sixes bust paid out rewards for moves it then reverted.** `LudoEnv.step()` returned the move reward (and incremented `_episode_captures_made`) immediately, but a later bust in the same turn restored `_turn_start_positions`, undoing the move. Confirmed with a scripted all-sixes RNG: the agent kept a `+1.0` capture reward and a counted capture while both tokens were returned to their pre-capture squares. Note `env/turns.py` already handled the opponent side correctly (returns `moves=[]` on a bust, so the agent's got-captured penalty is never applied) — so the two seats disagreed. Fixed by banking `_turn_move_reward`/`_turn_captures_made` per agent turn and refunding both on a bust, reusing the existing deferred-adjustment mechanism (`_pending_captured_penalty`, renamed `_pending_reward_adjustment` now that it carries refunds as well as penalties). This path had no test — `tests/test_turns.py` covers the bust only via `play_turn`, never through `LudoEnv`.
- 2026-09-22 — **The observation never contained the dice roll.** `encode_observation` took only the board, so the network learned Q(board, token) while the value of moving a token depends entirely on the roll — the same board mapped to six different true action-value vectors and only their average was learnable. The action mask leaked a sliver of roll information (only a 6 frees a Base token) and nothing more. Added as an opt-in `include_dice_roll` flag (`NUM_ROLL_FEATURES = 6`, one-hot, appended; absent roll at a terminal state encodes as all-zeros) rather than unconditionally, specifically so Step 10's existing 64-dim checkpoints still load and Step 11 can still evaluate them — `observation_size(include_dice_roll)` drives both the Gym space and `QNetwork`'s input layer, and `load_trained_policy` reads the flag back out of each run's saved config. Deliberately **not** applied to Tabular Q: adding the roll to `discretize_state` multiplies its state space by 6 (20,736 to 124,416), which is a separate experiment, not a free fix.
- 2026-09-22 — **gamma=0.95 made the terminal signal almost invisible.** Measured mean episode length at 121.7 agent decisions, so `0.95^121.7 ~ 1.9e-3` — the `+2.0` win reward was worth ~0.004 at episode start against per-step shaping of 0.2-1.0. The agents were therefore trained almost entirely by the shaping terms, with "win the game" barely in the objective; this is a strong candidate for the 7-8% plateau itself. It also meant Step 11.4's sparse ablation (win/loss only) was pre-destined to look near-random and would have measured the discount horizon rather than the value of shaping. `gamma` is left at 0.95 by default (so nothing silently diverges from Step 10) and raised explicitly in the pilot; `run_reward_ablation_training` now reads `gamma` and `include_dice_roll` from the dense arm's own saved config, so the sparse arm can never differ from its comparison arm on anything but the reward dict.
- 2026-09-22 — **`best.*` checkpoint selection was inert, and evaluation was unseeded.** `checkpoint_every_episodes` defaulted to 10000 against `num_episodes=10000`, so evaluation ran exactly once, at the final episode — verified: `best.pt` and `episode_10000.pt` are the same episode with the same `eval_win_rate` (0.06). The 2026-08-15 entry's justification ("DQN training curves aren't monotonic") described a mechanism that never actually ran. Separately, `evaluate()` reused the *training* env and its RNG, so each evaluation scored a different 50 games. Both fixed: the default is now 1000 (~23s of extra evaluation per 10,000-episode run), and each evaluation builds a fresh env on a fixed `EVAL_DICE_SEED_OFFSET + seed`, so every checkpoint in a run is scored on the identical game set and "best so far" is a real comparison.
- 2026-09-22 — **`save_config` snapshotted the dense reward dict unconditionally**, ignoring `reward_mode` — so every sparse run in 11.4 would have shipped a `config.json` claiming dense rewards, defeating the exact traceability purpose the snapshot was added for (2026-08-15). Now follows `config.reward_mode`.
- 2026-09-22 — **Statistics reworked to treat the seed as the unit of analysis.** `summarize_by_agent_type` pooled all seeds' games into one binomial and fed that to Wilson and the z-test — but the 5 seeds are 5 *different trained policies*, not 5 samples from one, so at 2000 games/seed the pooled CI is +/-0.5pp against a genuine across-seed CI of roughly [4.96%, 11.04%] on Step 10's DQN numbers. Reporting the pooled interval as the headline would have claimed about twelve times the precision actually available. Added `t_confidence_interval_across_seeds` (tabulated two-tailed t criticals, staying scipy-free per the 2026-08-17 entry) as the headline interval, kept the pooled figure explicitly labelled as aggregate play strength rather than method uncertainty, and added `holm_adjusted_p_values` since all agent types are tested against the same Random baseline and the p-values are a family. Also replaced the `capture_to_death_ratios` CSV column (a Python list literal in a cell, awkward for Step 12's figures) with mean/std, since the per-seed values are already in `tournament_results.csv`.
- 2026-09-22 — Every tournament in `run_all_tournaments` now uses one shared dice seed (`TOURNAMENT_SEED_OFFSET`) instead of `+ seed` per run, making the comparison paired: all agents face the identical sequence of games, so win-rate differences are policy differences rather than dice luck. Free variance reduction, available only before the tournament is run.
- 2026-09-22 — **Corrected the Heuristic reference number.** The 2026-08-17 entry estimated the Heuristic's own per-seat win rate at "~30%+". Measured directly (`heuristic_mirror`, one seat vs. 3 Heuristic, 400 games): **21.75%**, consistent with the ~25% expected by symmetry. The honest scale for the dissertation is therefore Random 4% to learned agents 6.8-8.0% to Heuristic ~22-25%, a smaller gap than previously described. Step 11's 2000-game `heuristic_mirror` will pin this down properly.
- 2026-09-22 — Logged but deliberately **not** fixed, as documented limitations rather than code changes: `apply_move` captures only the first opponent token on a square and scans players in id order (a rules variant plus a low-id bias, reachable when two different opponents share a non-safe square); `is_safe = 1.0` for Base and home-column tokens conflates three situations; the Heuristic baseline has no defensive logic (it is "greedy aggressive", and is simultaneously the opponent and the comparison ceiling); Tabular Q's greedy tie-break is deterministic toward the lowest token id on a zero-initialised table, so many evaluation decisions are "pick token 0" rather than learned. A 1200-game pure-engine run (all 4 seats via `play_turn`, no `LudoEnv`) gave seat win rates [22.9%, 24.8%, 28.6%, 23.7%], chi2=9.1, df=3, p~0.03 — weak, non-conclusive evidence of a seat asymmetry worth one dedicated invariant test later. Reassuringly, the `LudoEnv` mirror (21.75%) matches the pure-engine seat-0 figure (22.9%), so the agent's seat is *not* handled differently from the opponents' seats.
- 2026-09-22 — **The Step 10 hyperparameter sweep's winner is statistically indistinguishable from noise.** 12 configs ranked on 50 games each; the winning "14%" is 7 wins out of 50. If all 12 configs were truly identical at p=0.06, P(best >= 7/50) = 0.30, and the median best-minus-worst spread across 12 identical configs is 10pp against the 12pp actually observed. So the sweep provides essentially no evidence that lr=5e-4/sync=1000/decay=6000 is better than the alternatives — and that config was then used for all 10 DQN/Double-DQN final runs and is read back by 11.4's ablation. No code change (re-running the sweep at >=500 eval games is a compute decision, not a bug fix); this is recorded so the dissertation states the selection is within noise rather than presenting it as a tuned result.

## Step 11.5 — Pilot result (2026-09-22)

- 2026-09-22 — **Pilot: adding the dice roll to the observation and raising gamma to 0.99 produced no measurable improvement.** Two 10,000-episode DQN runs, seed 0, identical code and sweep hyperparameters, differing only in those two changes; evaluated by paired 2,000-game tournaments on one shared dice seed (one seat vs. 3 Heuristic). Final checkpoints: **treatment 7.60% vs. control 7.50%, z=0.12, p=0.91**. Best-by-eval checkpoints: 5.90% vs. 6.20%, z=-0.40, p=0.69. Both arms are comfortably above the Random baseline measured in the same tournament (4.30%; treatment vs. random z=4.41, p<0.0001), so learning is real in both — the two representation changes simply are not what was capping performance. Hypothesis falsified cleanly, at a cost of ~3 hours instead of the ~24 hours a full retrain would have taken. This is a genuine, reportable negative result for the dissertation's discussion: the 64-dim observation's omission of the roll, and the short effective discount horizon, were *plausible* explanations for the 7-8% plateau (both were logged as such on 2026-08-17) and both are now ruled out as primary causes by direct experiment rather than argument.
- 2026-09-22 — **Heuristic ceiling measured properly: 24.20%** over 2,000 games (95% CI [22.37%, 26.13%]), consistent with the 25% expected by symmetry when all four seats share a policy, and confirming the 400-game estimate of 21.75%. The definitive scale for the results chapter is therefore **Random 4.30% -> learned agents ~7.5% -> Heuristic 24.20%**, i.e. the learned agents close roughly 16% of the gap between random play and the hand-coded baseline.
- 2026-09-22 — **"Best checkpoint by evaluation win rate" selects *worse* models than simply taking the final checkpoint.** Now that `checkpoint_every_episodes=1000` makes the mechanism actually run (it was inert before — see the entry above), it can be tested: across both pilot arms the best-by-eval checkpoint scored 6.05% against the final checkpoint's 7.55% over 2,000 tournament games each (pooled z=-2.66, **p=0.008**). Cause: a 100-episode evaluation has a standard error of roughly 2.4pp, which is larger than the real differences between checkpoints, so taking the maximum over ten such estimates selects noise, and that optimism does not transfer to a fresh tournament. Consequence: `run_full_evaluation.load_trained_policy` loads `best.*`, so any future multi-eval run would be reported at a systematically pessimistic win rate. Step 10's completed runs are unaffected (they evaluated once, so `best` and `episode_10000` are the same checkpoint). Options are to select on the final checkpoint, or to raise `eval_episodes` to ~500 before trusting selection; flagged for decision rather than changed unilaterally, since it determines which model the dissertation reports.

## Step 11.6 — Move and threat features (2026-09-23)

- 2026-09-23 — Added two opt-in observation blocks for DQN: **move features** (32 values: for each token, whether moving it with the current roll is legal, captures, exits base, reaches home, forms a blockade, lands safe, escapes a threat, or ends in danger) and **threat features** (12 values: for each token, whether it is threatened, how close the nearest opponent behind is within 12 squares, and the smallest roll that would capture an opponent ahead). Rationale: the Heuristic opponent already sees the offensive half of the move features, and none of the defensive half or the threat features; the 64-value board observation encodes opponents in their own coordinate frames, so relative danger was effectively invisible to the network. Move features are computed by applying each legal move to a board copy with the real `apply_move`, so they cannot drift from the rules engine.
- 2026-09-23 — New `env/threats.py` is a rule-accurate "who can capture whom on the next roll" check, replacing the raw "any opponent 1-6 squares behind" approximation for these features: an attacker about to turn into its own home column is not a threat, blockades of any other player stop an attacker's path, and nothing is captured on a safe square. One roll ahead only; bonus-roll chains are not modelled. Tabular Q deliberately keeps its original `_is_threatened` check so its Step 10/11 results stay reproducible.
- 2026-09-23 — The observation switches (`include_dice_roll`, `include_move_features`, `include_threat_features`) are bundled into one `ObservationSpec` rather than threaded as parallel booleans, and all default off: with every switch off the observation is byte-for-byte the original 64 values (tested), so every existing checkpoint still loads. Measured cost: ~21 ms extra per episode (69 -> 90 ms gameplay-only), roughly 4% of a ~500 ms training episode.
- 2026-09-23 — **Step 11 now evaluates the final checkpoint, not `best`**, following the pilot finding that best-by-eval selects worse models (p=0.008). Verified this leaves every existing Step 10 result unchanged: all 15 `runs/full/final` runs have identical weights in `best` and `episode_10000`. It does **not** hold for the reward-ablation runs: four of the five sparse seeds' `best` checkpoints came from episodes 1000, 5000, 7000 and 6000, so the reported dqn_sparse 6.39% was measured on earlier, partly-trained checkpoints while every dense agent was measured on its final one. The dense-vs-sparse comparison (p=0.062) is therefore biased against the sparse arm and should be re-measured on final checkpoints before it is reported.

## Step 13 — DQN improvement Phase 2 (2026-09-29, Claude Sonnet 5)

- 2026-09-29 — **Phase 2.1: built `SharedTokenQNetwork`** (`agents/dqn_network.py`), selected via a new `network_type` switch on `DQNAgent`/`TrainingConfig` (values `"mlp"` default / `"shared_token"`). Instead of one MLP mapping the whole 108-value observation to 4 independent output units, it encodes the shared board context once (board + optional dice roll, 64 or 70 values) and scores each of the 4 tokens with the *same* small network applied to (context embedding, that token's own move features, that token's own threat features). The intent: every training experience updates the one shared scorer, so a lesson learned about "this move captures" or "this move ends in danger" for any token id transfers to all four, instead of the old design needing to relearn each pattern per token id. Verified by a direct test that two tokens given identical own-feature slices get identical Q-values. `training/run_full_evaluation.py::load_trained_policy` and `training/run_training.py` updated to pass `network_type` through so saved checkpoints reload with the right architecture. Full suite: 232 tests passing (was 226).
- 2026-09-29 — Phase 2.1 pilot launched: seed 0, 10,000 episodes, `network_type=shared_token`, otherwise identical to the 31.85% baseline (Phase 1's two changes were both rejected, so this pilot does not include Huber loss, gradient clipping, or the bigger batch/replay). Result pending.
- 2026-09-29 — The first Phase 2.1 pilot attempt was killed at episode ~4,761 of 10,000 by Claude Code's memory-pressure guard (not a code fault) and was rerun from scratch in an external terminal to `runs/dqn_improve/phase2_shared_token_seed0_rerun`, identical settings. The partial first attempt is not used.
- 2026-09-29 — **Phase 2.1 pilot (shared per-token network) rejected: 27.25% (545/2000, CI [25.34%, 29.24%]) vs the 31.85% baseline, a -4.60pp change.** Below the >= +3pp keep threshold and a real regression rather than noise (CIs barely overlap). Still above the Heuristic mirror (24.20%) and fair share (25%), so the model learned, just to a lower ceiling.
